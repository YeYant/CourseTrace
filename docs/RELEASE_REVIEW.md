## P1：发布预览版前优先修复

### R1 引用片段不对应检索命中位置（已复现）

位置：`app.py:237`；前端 `static/app.js` 的 `citation()` 只传资料、页码和哈希。

复现：使用 793 字符的单页原创 PDF，目标词位于后半页。检索命中 1 页，导出的 600 字符片段不包含目标词。
原因：引用统一采用页面最前面的 600 字符，命中位置没有传入引用流程。

影响：资料名称和页码仍正确，但用户点击结果后复制的正文可能与正在核对的知识点无关。这直接影响项目核心价值。

建议：

1. 检索返回原文中的命中起止位置和段落范围。
2. 阅读区明确展示「本次引用的片段」，支持选择某段；单纯浏览整页时允许只导出页级来源。
3. 服务端按页、版本哈希和范围从原文重取片段，不能直接信任客户端任意文本。
4. 如需截断，明确显示截断信息。

验收：首段、中段、末段命中，多处命中、中文/英文归一化匹配都能导出选定片段；旧版本和越界范围仍被拒绝。

### R2 移动文件夹会使上传副本失联（已复现）

位置：`app.py:109`、`app.py:150`，数据库 `documents.path` 保存绝对路径。

复现：在临时项目导入一份副本，再移动整个临时项目。新位置的 `data/files/` 中 PDF 仍存在，但状态变为 `missing`，检索结果为 0。

影响：换盘、移动桌面项目、恢复备份后，资料可能被误报为已移走；当旧目录仍在时，也可能继续读取旧副本。

建议：内部托管副本保存相对 data/ 的路径；外部跟踪文件保留绝对路径。增加数据库版本和迁移脚本，以及「重新定位原文件」操作。文件重定位先核验哈希；内容不同则明确更新版本并重新索引。

验收：移动整个项目后，所有上传副本正常检索和引用；外部资料行为不变；旧数据库迁移前自动备份，并能回滚。

### R3 一个未完成的请求会阻塞整个服务（已复现）

位置：`app.py:282`、`app.py:323`。

复现：本机测试服务收到声明 20 字节、实际只发送 1 字节且保持连接的 POST；另一连接的健康检查在 0.65 秒左右超时。关闭未完成连接后才能继续。

原因：先持有全局锁，再读取请求体，没有读取超时；此锁也包住静态文件、数据库操作、PDF 解析和响应写出。
断开测试连接时还出现未处理的 `ConnectionAbortedError` 日志。

影响：中断或停滞的上传、长时间 PDF 处理会使其他操作一起等待。这里是本机可靠性问题，不代表已确认可从公网访问。

建议：请求接收、长度验证、超时和响应写出放在 PDF 临界区之外；仅串行化确实需要串行的 MuPDF 操作。处理断连异常。对导入建立任务状态、进度和取消机制；PDF 解析可放到受控子进程，以便超时终止。

验收：不完整上传会在规定时间内退出；健康检查和页面静态资源仍能返回；取消导入不留下半成品记录；解析失败不会破坏已存在资料。

## P2：首发体验与工程准备

### R4 启动与端口冲突需要加固（部分已复现）

- 已复现：将健康检查响应模拟为合法 JSON 数组 `[]`，`launcher.py:14` 的 `.get()` 引发 AttributeError，启动器退出。
- 已确认代码：无虚拟环境时，批处理只尝试 `py -3`；不支持只有 `python` 命令的环境，也不检查最低 Python 版本。
- 已确认代码：8765 被其他应用占用时只能失败，没有自动换端口。
- 尚未确认：真实新 Windows 机器的安装体验、中文路径下人工双击，以及没有 Python 的电脑。

建议：验证健康响应的类型、应用名和根目录；探测可用 Python 与版本；支持端口回退，并把最终 URL 传给浏览器。先发布清楚标注依赖的源码版；面向普通学生可另做免 Python 的 Windows 包。

### R5 查询和翻页读盘开销偏大（读盘行为已复现，实际规模性能待测）

位置：`app.py:159`、`app.py:179`。
复现：资料库有 8 份 PDF，仅筛选其中 1 份搜索，仍读取全部 8 份 PDF 来校验哈希。

建议：建立文件状态缓存和后台变化检查，按所选资料缩小候选范围；元信息只作为变化筛查，正式导出仍核验文件哈希。预览按资料版本和页码缓存。之后再根据基准测试决定中文索引方案。

建议验收基准：在明确记载的参考电脑和测试语料上，分别测量 10、100、500 份资料的冷启动、热查询、翻页、内存和取消操作。可先把热查询低于 1 秒设为设计目标，不把它写成当前已达到的性能。

### R6 原页核对功能还不够顺手（代码确认）

当前原页是固定比例的图片，没有缩放、命中区域定位、原 PDF 打开入口，也没有印刷页码编辑或来源类型编辑。

建议优先顺序：原页放大和打开原 PDF → 在原页定位命中片段 → 编辑资料名称/类型 → 手工确认印刷页码 → 引用集合导出。
印刷页码需保存确认方式与确认状态，不要通过 PDF 页序自动推断。

## 建议推进顺序

第一轮：修 R1/R2/R3/R4，并把复现探针转为正式回归测试。

第二轮：加入基本缩放、原 PDF 打开入口、重定位和可编辑元信息；完成首发包与 CI。

第三轮：邀请 3–5 位愿意反馈的用户，用他们有权使用的真实课件试用。收集任务是否成功、失败 PDF 的最小复现、首次启动是否需要帮助；这个人数是建议，不是任何会员项目的门槛。

发布和开源会员申请分开评估：完成发布并不等于获得资格。之后应保留真实使用场景、反馈、修复和版本记录，不能用测试生成的数据代替真实影响力。
